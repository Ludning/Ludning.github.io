01State 패턴 몬스터 AI

AIStateMachine<T>가 IState<T>(OperateEnter / OperateUpdate / OperateExit)를 구현한 상태 객체를 들고 있다가 SetState() 호출 시 이전 상태의 Exit → 상태 교체 → 새 상태의 Enter를 순서대로 호출하는 제네릭 상태 머신입니다. 몬스터 타입에 관계없이 재사용할 수 있도록 설계했습니다.

02절차적 맵 생성 (이진 공간 분할 + 셀룰러 오토마타)

BinarySpacePartition이 맵을 사각형으로 재귀 분할(BSPNode.Partition())해 방 후보 영역을 만들고, 인접 노드 간 연결 리스트(GetAdjacencyList)로 방-방 연결 구조를 계산합니다. 여기에 CellularAutomata로 지형의 유기적인 형태를 결합했습니다.

03이벤트 버스 기반 UI 갱신

EventBusManager가 Dictionary<Type, Delegate> 기반 제네릭 Pub/Sub(Publish<T> / Subscribe<T>)을 제공하고, 스킬트리 UI가 EquipmentSkillEvent 등을 구독해 View와 데이터 변경을 분리했습니다.

04씬 인스톨러 / 퀘스트·상태이상

씬별 초기화를 담당하는 인스톨러(GameSceneInstaller, SkillTestSceneInstaller 등)로 기능 단위 테스트 씬을 구성했고, Quest – QuestCondition – Reward 조건-보상 구조의 퀘스트 시스템과 IStatusEffect 인터페이스 기반 상태이상 처리 구조를 구현했습니다.

Highlight

렌더링 순서 정리와 화면 밖 오브젝트 비활성화로 드로우콜을 최소화하는 최적화를 직접 수행했고, 제네릭 State 패턴·제네릭 이벤트 버스 등 재사용 가능한 구조 설계 경험을 이 프로젝트에서 처음 확립했습니다.

01데이터 드리븐 스킬 시스템

GameData(Odin SerializedScriptableObject)가 Dictionary<int, SkillData>로 스킬을 관리하고, 각 SkillData는 List<SkillElement>를 가집니다. SkillElement 하나가 skillType·damageType·effectType·buffType·costType 등의 필드로 구성되어 하나의 스킬을 여러 "조건-효과 조합" 행으로 표현합니다. Editor/Converter/DataConverter.cs는 ExcelDataReader로 읽은 시트를 리플렉션(FieldInfo, MakeGenericMethod)으로 자동 변환해 ScriptableObject에 채워 넣습니다.

02MVVM 패턴 UI

ViewBase<TViewModel, TMessage> / ViewModelBase<TMessage> 제네릭 베이스로 골격을 구성했습니다. 뷰모델은 MessageManager(타입별 델리게이트 Pub/Sub)로 메시지를 구독하고 INotifyPropertyChanged로 뷰에 변경을 알립니다. BossHp / Buff / PlayerHp / PlayerMp / SkillPanal이 이 베이스를 상속합니다.

03비헤이비어 트리 몬스터 AI · 아이템 조합 구조

Behavior Designer로 Action(AttackPattern, Patrol, TrackingTarget)·Conditional·SharedVariable을 조합해 AI를 구성했고, ItemBase / ArchetypeBase(원형) / SpecificityBase(세부 특성)로 아이템 종류가 늘어나도 속성 조합만으로 확장 가능한 구조를 설계했습니다.

Retrospective

"조건·효과를 데이터 테이블에 작성하는 방식은 파싱이 복잡하고 오타 가능성이 있다"는 한계를 직접 경험했고, 이런 경우 전용 스킬 데이터 에디터 툴을 만드는 편이 더 효율적이라는 결론을 얻었습니다. 이 문제의식은 이후 로보쿡드의 맵 에디터 툴과 Gluttony의 업그레이드 파이프라인으로 이어집니다.

01함수 블록 기반 블록코딩 시스템

BlockLogicBase를 상속한 블록(MoveLogic, RotateLeftLogic, DashLogic, PushItemLogic, RepeatBlockLogic, CookLogic 등)이 IsExecutable() · Execute() · CheakClear()를 오버라이드하는 공통 인터페이스로 동작합니다. 예를 들어 CookLogic은 바닥 타일 → 조리 가능 지형 → 재료 존재 → 레시피 매칭을 순서대로 검사한 뒤 GameManager.FindPossibleRecipes()로 완성 음식을 판정합니다. 블록을 Sheet(MainSheet/ExSheet/RepeatSheet)에 배치해 코드 없이 로직을 조립할 수 있게 했습니다.

02자체 제작 맵 에디터 툴

MapEditorTool은 UI Toolkit(EditorWindow + UnityEngine.UIElements)으로 만든 커스텀 에디터로, 툴바·MapDrawSpace(그리기 영역)·TilePalette·Inspector·MapInfoListView로 구성된 완전한 그래픽 툴입니다. 기획팀이 코드를 몰라도 맵을 직접 만들고 수정할 수 있도록 제작했습니다.

03UniTask 비동기 처리 · VR 인터랙션

블록 오브젝트 생명주기 관리에 UniTaskVoid + Forget() 패턴을 사용했고, Meta Interaction SDK의 InteractableUnityEventWrapper 이벤트로 VR 핸드 인터랙션을 구현했습니다.

Retrospective

Singleton<T> / SingletonMonoBehaviour<T> 기반 매니저 구조가 SOLID(특히 의존성 역전) 원칙에 어긋난다는 점을 인식하고 사용을 최소화하려 했으나, 규모가 커지며 참조 관계 관리가 까다로워지는 한계를 경험했습니다. "단점 없는 패턴은 없으며 적재적소로 사용하는 것이 중요하다"는 결론을 이 프로젝트에서 얻었습니다.

Ⅰ. 브랜치 이동 전 — PROJECT_FG 시기

2024.12.20 – 2025.12.03 · 305 커밋 · 신규 스크립트 약 200개

01보스 AI · 상태 머신

EnemyController(제네릭 FSM<EnemyController>)를 상속한 BossController를 파셜 클래스로 분리(본체 / BossController.FSM.cs 상태 전이)해 대형 컨트롤러의 가독성과 팀 병렬 작업 시 머지 충돌을 관리했습니다. 모든 상태 전이 조건식 상단에 동일한 인터럽트 우선순위(빙결 → 사망/그로기 → 상태별 고유 전이)를 두어 예외 처리를 한 곳에 모았습니다.

02보스 스킬 · 패링/처형 시스템

보스 패턴을 스킬 액션 단위로 모듈화하고 수치·조건은 BossSkillData로 분리했습니다. BossSkillManager가 SkillState(Ready/Running/Finished)로 FSM과 연동하고, 패링 성공 시 스턴 진입 · 실패 시 페널티까지 모두 데이터로 분리해 밸런싱 가능한 패링 → 스턴 → 처형 루프를 구현했습니다.

03보스 강화(렐릭) 시스템

하나의 강화를 조건(언제/만약) + 효과(무엇을) 조합으로 설계해 30종 이상을 코드 분기 없이 데이터로 정의했습니다. BossUpgradeFactory가 enum을 받아 조건·동작 객체를 생성(전략+팩토리 패턴)하고, ExecutionStack으로 스택 추가 시 이전 효과를 제거 후 재적용해 항상 원복 가능하게 만들었습니다.

  • 01대형 클래스(BossController) 유지보수 부담→파셜 클래스로 본체/상태전이/스킬연동 분리, 머지 충돌 완화
  • 02강화 종류가 늘수록 프로그래머 병목→조건+효과 데이터 구동 구조로 전환
  • 03매 시전 콜라이더 생성/파괴로 프레임 드랍→오브젝트 풀링 도입
  • 04투사체 종류 증가로 상속 조합 폭발→"Info 컴포넌트 조합" 방식으로 전환

Ⅱ. 브랜치 이동 후 — 현재 시기

2025.12.09 – 2026.09.05 · 277 커밋 · 순증 약 +11,300라인

01업그레이드 파이프라인 — 리플렉션 자동 등록

효과 하나를 트리거(언제) → 조건(만약) → 효과(무엇을) 3단으로 분해해, 기획자가 스프레드시트만으로 100종 이상의 업그레이드를 조립할 수 있게 했습니다. 기존 약 150줄짜리 switch 팩토리를 [Executor(ExecutorType.XXX)] 커스텀 어트리뷰트 + 리플렉션으로 정적 생성자에서 자동 등록하는 구조로 리팩토링해, 신규 효과 추가가 "클래스 파일 1개 작성"으로 끝나도록 만들었습니다.

02아웃게임 스킬트리 — MVP, 100% 개인 작업

모델(SkillTreeModel→NodeModel→ElementModel) / 프리젠터(순수 C#) / 뷰(MonoBehaviour) 3계층, 22개 파일로 분리 설계했습니다. 프리젠터는 모델과 뷰를 중재만 하는 순수 C# 클래스라 로직 단위 테스트·재사용이 가능하고, 노드 스스로가 아니라 SkillTreePresenter가 구매·리셋마다 전체 노드를 일괄 재계산해 순환·누락 문제를 없앴습니다.

03투사체 시스템 (13종)

ProjectileBase(약 985줄)가 관통 수·도탄 횟수·파생 투사체·속도/사거리/감쇠 등을 데이터 주도 파라미터로 노출하고 OnStart / OnEnemyHit / OnEnemyDie 이벤트로 업그레이드·스킬이 훅을 겁니다. 이를 바탕으로 지뢰형·수류탄·궤도 회전·유도·히트스캔·부메랑·AOE 등 13종을 직접 구현했습니다.

04푸드파워 스킬 · 버프 시스템

SkillBase(약 1,470줄) → FoodPowerSkill 파생 구조로 "레벨 데이터 + 스킬 강화 + 전역 보정"을 더하는 레이어드 스탯 해석을 구현했습니다. BuffHandler(약 630줄)는 빙결·화상·기절 등 상태이상 20종을 관리하며, 일반 버프와 중첩 배율 계산이 필요한 버프를 리스트를 분리해 운용합니다. 버프는 증가 속도가 느려 의도적으로 switch 팩토리를 유지 — 업그레이드(리플렉션 자동 등록)와 규모·변화 빈도에 따라 팩토리 전략을 다르게 선택한 사례입니다.

  • 01업그레이드 팩토리 비대화→커스텀 어트리뷰트+리플렉션 자동 등록, 신규 효과 추가가 클래스 1개로 축소
  • 02누적형 효과가 세이브/로드에서 깨짐→orderIndex 참조 전달로 순서 보장하며 복원
  • 03스킬트리 노드가 중앙 매니저에 강결합→노드 자체 초기화 + Presenter 일괄 재계산 (MVP 분리)
  • 04런타임 투사체 프리팹 교체 시 데이터 유실·중복 생성→고유값 이관 시점 정리 + 억제 플래그 도입
  • 05릴리스 빌드 크래시 (보스 투사체 Null 예외)→세이브 로드 루프 가드 누락 수정, v0.2.x 안정화
